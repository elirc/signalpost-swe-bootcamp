# U09 — Data structures and measured performance

**Independent delivery · Learning unassessed.** Choose suitable data structures and verify performance against a defined workload.

Prerequisites: U08. Challenge-out requires evidence; see ASSESSMENT.md.

## Learn

Arrays, maps, sets, stacks and queues support different access patterns. Big-O describes growth under an explicit model; it does not predict response time on particular hardware. Recognize repeated scans and unbounded work before optimizing syntax. Define a workload, symptom and correctness oracle; distinguish CPU, I/O and waiting. Compare multiple sizes, warmup and repeated trials. Inspect database plans or browser profiles at the actual bottleneck. Caching adds memory and invalidation obligations.

- Practice linear scan, binary search on sorted input, map/set lookup and queue processing.
- State both time and space cost and any precondition.
- Averages can hide slow requests; examine distribution and variation.
- Measure the generator too; faster wrong output is not an improvement.

## Worked example

```text
N tasks each scan M projects: up to N × M comparisons.
Build a project Map once: M inserts, then N lookups under the usual average lookup model.
Cost: memory and a rebuild/invalidation policy when names change.
```

A map removes repeated scans, but small input may not get faster in wall time. Prove identical behavior and measure relevant sizes before claiming improvement.

## Guided practice

1. Implement and trace a stack and queue on tiny problems.
2. Trace binary search for first, last and missing values.
3. Compare both project-lookup approaches on five tasks.
4. Profile your learner app before selecting an optimization.
