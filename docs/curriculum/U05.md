# U05 — SQL, integrity and transactions

**Foundations · Learning unassessed.** Persist the API and prove failed changes preserve valid data.

Prerequisites: U04. Challenge-out requires evidence; see ASSESSMENT.md.

## Learn

A relational schema describes entities and relationships; constraints reject invalid state even when callers make mistakes. Learn SELECT, INSERT, UPDATE, DELETE and JOIN with tiny datasets before an ORM. A transaction groups changes that commit or roll back together. Parameterize values instead of building SQL with untrusted text. A uniqueness pre-check can race; the database constraint must enforce the rule. Choose indexes from access paths and inspect the plan. Embedded PostgreSQL practice teaches semantics; it does not prove networked concurrency or host-crash durability.

- Keys identify rows; foreign keys enforce relationships.
- NULL means missing/unknown; use IS NULL for that predicate.
- NOT NULL and CHECK express different promises.
- A migration needs populated-data upgrade and recovery evidence.

## Worked example

```text
CREATE TABLE books (id integer PRIMARY KEY, title text NOT NULL, pages integer CHECK (pages > 0));
INSERT INTO books VALUES (1,'Small Systems',120);
SELECT title FROM books WHERE pages >= 100;
```

A duplicate id fails. NOT NULL title still permits an empty string. The pages check rejects zero but permits NULL unless a separate NOT NULL constraint forbids it. Test the promise each constraint actually makes.
